# План переработки документации

Документ предназначен для ИИ-агентов. Цель: привести `docs/` к состоянию, где документы отражают текущий код, а планы и будущие решения явно отделены от фактической документации.

Актуально на 28.05.2026.

## 1. Проблема

В `docs/` накопились документы разных типов:

- фактическая архитектура;
- пользовательские руководства;
- эксплуатационные runbook;
- бизнес-описания;
- старые migration-планы;
- новые планы рефакторинга.

Главная проблема: часть документов смешивает текущее состояние, целевую архитектуру и исторические планы. Из-за этого агент может принять будущую задумку за уже реализованный код.

## 2. Цель

Нужно получить документацию с четким разделением:

- **факты** — что реально есть в коде сейчас;
- **инструкции** — как пользоваться и эксплуатировать текущую систему;
- **планы** — что нужно переработать в будущем;
- **архив** — исторические решения, которые нельзя использовать как актуальную инструкцию.

## 3. Принципы

### 3.1 Код важнее документа

Если документ спорит с кодом, источник истины:

1. `prisma/schema.prisma`
2. `server/routes/*`
3. `server/services/*`
4. `src/App.tsx`
5. `src/admin/*`, `src/partner/*`, `src/public/*`
6. `electron/hq/*`
7. `package.json`
8. `tests/e2e/*`

### 3.2 Планы не должны выглядеть как факты

Документы-планы должны иметь в названии `PLAN` или явно говорить в первом абзаце, что это план.

Примеры:

- `VIDEO_TOOL_WORKFLOW_REFACTOR_PLAN_RU.md`
- `DOCUMENTATION_REFACTOR_PLAN_RU.md`

### 3.3 Исторический документ нельзя использовать как runbook

Если документ описывает старую миграцию или уже пройденный этап, он должен быть:

- заменен фактическим статусом;
- либо перенесен в архив;
- либо явно помечен как исторический.

## 5. Крупные этапы переработки

## Этап 1. Разметить документы по типам

Для каждого файла в `docs/` указать тип:

- `actual` — фактическая документация;
- `guide` — пользовательская инструкция;
- `ops` — эксплуатационная инструкция;
- `business` — бизнес-описание;
- `plan` — будущая работа;
- `archive` — исторический материал.

Результат:

- `docs/README.md` содержит актуальный список документов по типам;
- планы не смешаны с фактическими инструкциями.

## Этап 2. Проверить технические документы по коду

Проверить:

- команды из `package.json`;
- route-модули из `server/routes/*`;
- Prisma models/enums из `prisma/schema.prisma`;
- Electron modules из `electron/hq/*`;
- реальные frontend routes из `src/App.tsx`;
- e2e routes из `tests/e2e/*`.

Документы:

- `ARCHITECTURE.md`
- `TEST_CREDENTIALS_AND_TECH_INFO_RU.md`
- `DOCKER_RU.md`
- `OPERATIONS.md`
- `ELECTRON_ADMIN_MIGRATION_RU.md`

Что исправлять:

- несуществующие команды;
- несуществующие endpoints;
- устаревшие названия статусов;
- утверждения “работает автоматически”, если код требует ручного действия;
- описание целевой архитектуры как текущей.

## Этап 3. Проверить пользовательские руководства по UI

Проверить:

- реальные маршруты в `src/App.tsx`;
- названия разделов в `src/admin/*` и `src/partner/*`;
- доступность действий по ролям;
- текущие ограничения Video Tool;
- текущие ограничения финансового кабинета;
- публичный clone/QR flow.

Документы:

- `SYSTEM_USAGE_GUIDE_RU.md`
- `USER_GUIDE_ADMIN_RU.md`
- `USER_GUIDE_FRANCHISEE_RU.md`
- `USER_GUIDE_OWNER_RU.md`

Что исправлять:

- действия, которых нет в UI;
- устаревшие названия кнопок;
- обещания автоматизации, которой нет;
- инструкции по старому Video Tool flow без пометки legacy.

## Этап 4. Проверить бизнес-документы по доменной модели

Проверить:

- роли;
- enum-статусы;
- переходы заказов;
- переходы collection workflow;
- переходы batch;
- item statuses;
- цифровой паспорт;
- финансовые операции;
- Telegram-side-effects.

Документы:

- `BUSINESS_LOGIC_RU.md`
- `BUSINESS_PROCESS_MAP_RU.md`
- `BUSINESS_PROCESSES_AUDIT_RU.md`

Что исправлять:

- статусы, которых нет в Prisma;
- переходы, которых нет в API;
- процессы, которые описаны как реализованные, но в UI/route отсутствуют;
- старые seed-only сценарии без пометки.

## Этап 5. Сократить дублирование

Текущий риск: одна и та же логика описана в нескольких местах.

Целевое правило:

- детальная бизнес-логика — только в `BUSINESS_LOGIC_RU.md`;
- краткое пользовательское объяснение — в user guides;
- route/API список — в `TEST_CREDENTIALS_AND_TECH_INFO_RU.md`;
- архитектурные связи — в `ARCHITECTURE.md`;
- планы — только в `*_PLAN_*.md`.

Если информация нужна в нескольких документах, второй документ должен давать краткую ссылку, а не копировать полный блок.

## Этап 6. Ввести “документ устарел” для сомнительных файлов

Если агент не может быстро проверить большой документ:

- не переписывать его наугад;
- добавить верхний блок `Статус проверки`;
- перечислить непроверенные разделы;
- не использовать этот документ как источник истины до аудита.

Формат:

```md
> Статус проверки: частично проверено по коду на YYYY-MM-DD.
> Непроверенные разделы: ...
```

## Этап 7. Финальная приемка docs

Перед сдачей документационного рефактора:

```bash
rg -n "как должно быть|что нужно сделать|будет|планируется|TODO|TBD" docs
rg -n "video-export-sessions|video-export-runs|helper|desktop" docs
rg -n "npm run|/api/|/admin/|/partner/|/clone/" docs
```

Проверить вручную найденные места:

- будущие формулировки должны быть только в планах;
- endpoints должны существовать в коде;
- команды должны существовать в `package.json`;
- маршруты должны существовать в frontend/backend.

Для изменений только в документации тесты приложения не обязательны. Достаточно проверить diff и отсутствие явных противоречий.

## 7. Запрещенные подходы

Не делать:

- удалять бизнес-правила без проверки по Prisma/API;
- переписывать пользовательские инструкции по памяти;
- выдавать планы за реализованное состояние;
- оставлять большие исторические документы без статуса;
- менять код ради документации в рамках этого рефактора;
- удалять тестовые креды без синхронной проверки seed/e2e.
