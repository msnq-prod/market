# Раздел «Товары»: целевые бизнес-процессы

## 1. Назначение документа

Документ описывает целевую структуру раздела `Товары` исключительно через бизнес-процессы.

Это не описание текущего интерфейса и не требование сохранить существующие страницы.

Главный принцип:

- один пункт меню открывает готовый рабочий интерфейс;
- пользователь не выбирает сценарий повторно внутри страницы;
- промежуточных кнопок `Открыть ...` нет;
- информация показывается только тогда, когда помогает выполнить действие;
- мобильное меню в рамках этой проработки не изменяется.

## 2. Пользователь и зона ответственности

Единственный основной пользователь раздела — `ADMIN`.

Администратор контролирует весь путь товара:

1. создает локацию;
2. создает товарный шаблон;
3. создает заказ на партию;
4. принимает прибывшую партию;
5. назначает фото каждому Item;
6. готовит и назначает видео каждому Item;
7. печатает QR-коды при необходимости;
8. вручную запускает проверку готовности;
9. передает партию на склад;
10. управляет списанием и возвратом Item на склад.

## 3. Основная модель процесса

### 3.1 Начало процесса

Путь товара начинается с подготовки трех сущностей:

- локация происхождения;
- товарный шаблон;
- заказ на партию.

### 3.2 Партия и Item

Партия — рабочая группировка множества Item.

Операции выполняются в контексте партии, но уникальные данные принадлежат отдельным Item:

- серийный номер;
- ссылка цифрового паспорта;
- QR-код;
- фото;
- видео;
- складское состояние.

Item не проходит отдельный независимый производственный процесс. Его состояние определяется состоянием партии, кроме индивидуальных media, серийного номера и складских операций.

### 3.3 Завершение товарного процесса

Товарный процесс завершается передачей партии на склад.

Партия может перейти на склад только после ручного запуска проверки администратором.

Проверка должна подтвердить:

- у каждого Item есть фото;
- у каждого Item есть видео;
- серийные номера не дублируются.

Автоматического перехода на склад нет, даже если все условия уже выполнены.

После успешной проверки:

- партия считается завершенной;
- Item попадают на склад;
- каждый несписанный Item считается доступным к продаже.

Отдельного процесса распределения между `складом` и `продажей` не требуется.

## 4. Целевая структура меню

Раздел `Товары` должен содержать следующие прямые рабочие сценарии:

1. `Очередь`
2. `Локации`
3. `Товарные шаблоны`
4. `Заказы на партии`
5. `Приемка`
6. `Фото`
7. `Видео`
8. `QR и паспорта`
9. `На склад`
10. `Склад`

Пункт `Распределение` в целевой модели отсутствует.

## 5. Сценарий «Очередь»

### Цель

Показать администратору следующую необходимую работу без поиска по разделам.

### Приоритет отображения

1. Партии без полного комплекта фото.
2. Партии без полного комплекта видео.
3. Партии с завершенной media-подготовкой, ожидающие ручной проверки.
4. Партии, проверка которых завершилась ошибкой.
5. Недавно переданные на склад партии.

### Для каждой партии показывается

- товарный шаблон;
- локация;
- количество Item;
- состояние партии;
- количество готовых фото;
- количество готовых видео;
- наличие конфликтов серийных номеров;
- следующее допустимое действие.

### Действия

- открыть назначение фото;
- открыть подготовку видео;
- открыть проверку готовности;
- открыть ошибки проверки;
- открыть карточку партии.

Действие должно сразу открывать соответствующий рабочий интерфейс выбранной партии.

## 6. Сценарий «Локации»

### Цель

Создать и поддерживать точки происхождения товаров.

### Функции

- создать локацию;
- изменить данные локации;
- изменить координаты;
- изменить изображение;
- изменить тексты и переводы;
- скрыть локацию обратимым способом;
- восстановить скрытую локацию;
- увидеть связанные товарные шаблоны и партии.

### Поля

Обязательные:

- название;
- страна;
- широта;
- долгота.

Дополнительные:

- описание;
- изображение;
- переводы;
- положение подписи на планете для desktop и mobile.

### Ограничения

- удаление не должно быть необратимым;
- изменение локации не должно незаметно разрушать связи с товарами и партиями;
- опасные изменения требуют подтверждения.

### Результат

Локация готова для создания товарных шаблонов и заказов на партии.

## 7. Сценарий «Товарные шаблоны»

### Цель

Описать тип товара, по которому создаются заказы и партии.

### Функции

- создать товарный шаблон;
- привязать его к локации;
- изменить название и описание;
- изменить цену;
- изменить коды и служебные поля;
- изменить переводы;
- изменить изображение шаблона;
- скрыть шаблон обратимым способом;
- восстановить шаблон;
- открыть связанные заказы, партии и складские Item.

### Поля

Обязательные:

- название;
- описание товара;
- цена;
- категория;
- локация;
- код страны;
- код локации;
- код товара.

Дополнительные:

- описание места;
- изображение;
- ссылки Wildberries и Ozon;
- переводы;
- состояние публикации.

### Важное разделение

Изображение товарного шаблона не заменяет индивидуальные фото и видео Item.

### Результат

Шаблон готов для создания заказа на партию.

## 8. Сценарий «Заказы на партии»

### Цель

Создать задание на получение физической партии.

### Функции

- создать заказ;
- выбрать товарный шаблон;
- указать количество Item;
- выбрать исполнителя;
- добавить заметку;
- изменить заказ до создания или отправки партии;
- отменить заказ обратимым способом;
- восстановить отмененный заказ;
- видеть состояние исполнения;
- открыть связанную партию после ее создания.

### Состав заказа

- один товарный шаблон;
- одна локация, определяемая выбранным шаблоном;
- количество Item от 1 до 999;
- исполнитель;
- заметка.

### Исполнитель

- конкретный партнер;
- общий пул партнеров;
- администратор, создавший заказ, в сценарии автоприемки.

### Создание партии партнером

При завершении заказа партнер указывает:

- GPS-широту;
- GPS-долготу;
- дату сбора;
- время сбора.

### Автоприемка администратором

Администратор создает и сразу принимает партию в контексте заказа.

Для партии указываются:

- координаты;
- дата сбора;
- время сбора.

### Результат

Создан заказ, по которому ожидается физическая партия.

### Основные состояния

- черновик;
- создан;
- выполняется;
- партия в пути;
- партия принята;
- партия передана на склад;
- отменен.

Точный набор и названия состояний требуют отдельного утверждения.

## 9. Сценарий «Приемка»

### Цель

Зафиксировать фактическое получение партии администратором.

### Рабочая очередь

Показываются партии, которые ожидают физической приемки.

### Для выбранной партии показывается

- локация;
- товарный шаблон;
- ожидаемое количество Item;
- фактически принятое количество;
- идентификаторы Item;
- серийные номера;
- состояние партии.

### Действия администратора

1. Проверить количество физических товаров.
2. Зафиксировать фактическое количество.
3. Нажать `Принять партию`.

### Результат приемки

- партия становится принятой;
- для Item становятся доступны цифровые паспорта;
- QR-коды можно печатать;
- партия появляется в очередях `Фото` и `Видео`.

### Изменение количества

При приемке администратор может изменить фактическое количество Item в партии.

После подтверждения система должна привести состав партии к указанному количеству:

- добавить недостающие Item;
- убрать лишние Item обратимым способом;
- сохранить изменение в журнале действий;
- пересчитать последовательность Item;
- проверить уникальность новых серийных номеров.

### Ограничения

- Item не отклоняются поштучно;
- проверка качества выполняется физически и не дублируется сложным UI;
- все действия должны быть обратимыми.

### Отмена приемки

Администратор выбирает партию и нажимает отдельную кнопку отмены приемки.

Отмена:

- возвращает партию в предыдущее состояние;
- не удаляет Item и media;
- фиксируется в журнале;
- не требует обязательного указания причины.

## 10. Сценарий «Фото»

### Цель

Назначить индивидуальные фотографии каждому Item принятой партии.

### Рабочая очередь

Показываются принятые партии, в которых хотя бы у одного Item отсутствует фото.

### Для партии показывается

- общее количество Item;
- количество Item с фото;
- количество Item без фото;
- последовательность Item;
- серийные номера;
- состояние сохранения и загрузки.

### Функции

- выбрать партию;
- загрузить фотографии;
- сопоставить фотографии с Item;
- изменить назначение;
- удалить ошибочное назначение;
- сохранить назначения;
- повторить неудачную загрузку;
- увидеть Item без фото;
- отменить изменения до сохранения;
- восстановить предыдущее сохраненное назначение.

### Результат

Каждый Item партии имеет ровно одно обязательное индивидуальное фото.

### Ограничения

- фото сохраняется у Item, а не у партии;
- партия не может перейти на склад, пока есть Item без фото;
- наличие полного комплекта фото само по себе не меняет состояние партии.

## 11. Сценарий «Видео»

### Цель

Подготовить и назначить индивидуальное видео каждому Item принятой партии.

### Рабочая очередь

Показываются принятые партии, в которых хотя бы у одного Item отсутствует финальное видео.

### Для партии показывается

- количество Item;
- количество подготовленных видео;
- количество отсутствующих видео;
- состояние исходного файла;
- состояние нарезки;
- состояние экспорта;
- состояние загрузки каждого результата.

### Функции

- выбрать партию;
- загрузить или выбрать исходное видео;
- разметить фрагменты;
- сопоставить фрагменты с Item;
- запустить экспорт;
- видеть прогресс каждого Item;
- повторить неудачный экспорт;
- повторить неудачную загрузку;
- изменить сопоставление;
- восстановить предыдущий результат.

### Результат

Каждый Item партии имеет ровно одно обязательное индивидуальное видео.

### Ограничения

- видео сохраняется у Item, а не у партии;
- партия не может перейти на склад, пока есть Item без видео;
- завершение экспорта само по себе не меняет состояние партии.

## 12. Сценарий «QR и паспорта»

### Цель

Работать с идентификацией принятых Item независимо от media-готовности партии.

### Доступность

Сценарий становится доступен после приемки партии.

Публичный паспорт доступен сразу после приемки, даже если фото и видео еще не назначены.

### Функции

- выбрать принятую партию;
- видеть Item и серийные номера;
- открыть ссылку цифрового паспорта;
- скопировать ссылку;
- сформировать QR для всей партии;
- выбрать отдельные Item;
- напечатать QR выбранных Item;
- повторно напечатать QR;
- изменить макет печати;
- изменить серийный номер;
- проверить уникальность серийного номера;
- восстановить предыдущее значение серийного номера.

### Правила

- QR-код ведет на цифровой паспорт конкретного Item;
- QR можно печатать в любой момент после приемки;
- повторная печать не меняет состояние Item или партии;
- изменение серийного номера является опасной операцией;
- изменение требует явного подтверждения;
- серийный номер изменяется только для одного Item;
- массовое изменение серийных номеров запрещено;
- дублирование серийного номера запрещено;
- изменение фиксируется в журнале действий.

### Формирование серийного номера

Серийный номер формируется по действующему правилу:

1. код страны товарного шаблона;
2. код локации товарного шаблона;
3. код товара;
4. дата сбора в формате `DDMMYY`;
5. порядковый номер Item в партии в формате `001`;
6. если в один день для шаблона создано несколько партий, перед основой добавляется номер партии за день.

## 13. Сценарий «На склад»

### Цель

Вручную проверить готовность партии и завершить товарный процесс.

### Рабочая очередь

Показываются принятые партии в следующем порядке:

1. полный комплект media, готовые к проверке;
2. неполный комплект media;
3. ошибка предыдущей проверки.

### Для партии показывается

- количество Item;
- количество готовых фото;
- количество готовых видео;
- количество Item с полным media;
- количество конфликтов серийных номеров;
- состояние последней проверки.

### Основное действие

`Проверить и передать на склад`.

### Проверки по нажатию

- каждый Item имеет фото;
- каждый Item имеет видео;
- каждый Item имеет уникальный серийный номер;
- партия находится в допустимом состоянии.

### Успешный результат

- партия считается завершенной;
- Item переходят на склад;
- несписанные Item становятся доступными к продаже.

### Ошибки

Если проверка не пройдена, состояние партии не меняется.

Интерфейс должен показать конкретно:

- какие Item не имеют фото;
- какие Item не имеют видео;
- какие серийные номера дублируются;
- какое действие исправляет каждую проблему.

### Обратимость

Администратор выбирает партию и нажимает отдельную кнопку отмены передачи на склад.

Отмена:

- возвращает партию в принятое состояние;
- возвращает Item из складского состояния в подготовку;
- сохраняет фото, видео, паспорта и QR;
- фиксируется в журнале;
- не требует обязательного указания причины.

## 14. Сценарий «Склад»

### Цель

Контролировать Item, завершившие товарный процесс.

### Для каждого Item показывается

- локация;
- товарный шаблон;
- партия;
- серийный номер;
- фото;
- видео;
- ссылка паспорта;
- складское состояние;
- состояние списания.

### Функции

- искать и фильтровать Item;
- открывать Item;
- открывать исходную партию;
- просматривать media;
- открывать паспорт;
- печатать QR;
- списать Item;
- вернуть списанный Item на склад;
- выполнять операции для выбранной группы Item;
- видеть историю изменений отдельно от основного интерфейса.

### Правила доступности к продаже

Item доступен к продаже, если:

- находится на складе;
- не списан.

Отдельное ручное распределение в онлайн-продажу не требуется.

### Обратимость

- списание должно быть обратимым;
- возврат на склад должен восстанавливать доступность Item;
- причина списания или возврата не обязательна;
- история операций должна сохраняться;
- опасные массовые действия требуют подтверждения.

## 15. Общие правила состояний

- Все переходы запускает администратор.
- Система не переводит партию на следующий этап автоматически.
- Система может выполнять проверки, но изменение состояния происходит только после явного действия.
- Item наследуют рабочее состояние партии.
- Индивидуально у Item хранятся media, серийный номер, паспорт, QR и складское состояние.
- Item не отклоняются.
- Консигнация не используется.
- Продажа не входит в товарный процесс.
- Все действия должны быть обратимыми или иметь компенсирующее действие.
- Для каждого Item обязательны одно фото и одно видео.
- Серийные номера изменяются только по одному Item.
- Паспорт доступен сразу после приемки партии.

## 16. Ошибки, блокирующие процесс

Передачу партии на склад блокируют:

- отсутствие фото хотя бы у одного Item;
- отсутствие видео хотя бы у одного Item;
- дублирование серийных номеров.

Ошибки должны показываться рядом с конкретными Item, а не только общим сообщением.

## 17. Журнал действий

Журнал не должен занимать место в основном рабочем интерфейсе.

Он должен быть доступен отдельно и фиксировать:

- пользователя;
- дату и время;
- сущность;
- предыдущее значение;
- новое значение;
- выполненное действие;
- причину опасной операции;
- результат проверки или восстановления.

Обязательно журналируются:

- приемка партии;
- изменение количества;
- изменение серийного номера;
- назначения и замены media;
- передача на склад;
- отмена передачи на склад;
- списание;
- возврат на склад.

## 18. Что не входит в раздел

В разделе `Товары` не должно быть функций, не связанных с физическим товарным процессом.

Отдельно остаются:

- обработка заказов покупателей;
- доставка покупателю;
- возврат покупателя;
- клиентская база;
- финансовые операции;
- пользователи и роли;
- Telegram;
- системная диагностика.

## 19. Открытые решения

Основные решения по процессу утверждены.

Перед реализацией интерфейса остается проверить только техническую совместимость:

1. поддерживает ли backend изменение количества уже созданных Item при приемке;
2. поддерживает ли backend отмену приемки без удаления партии;
3. поддерживает ли backend возврат завершенной партии со склада в подготовку;
4. доступен ли публичный паспорт принятой партии до появления media;
5. должна ли публикация товарного шаблона влиять на видимость складского Item в продаже.
