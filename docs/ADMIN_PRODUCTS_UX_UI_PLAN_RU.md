# UX/UI-план нового раздела «Товары»

## 1. Цель

Создать единый рабочий раздел, в котором администратор управляет полным путем физического товара:

`локация → шаблон → заказ на партию → приемка → фото → видео → QR/паспорт → проверка → склад`.

Главный UX-принцип:

> Один выбор в меню сразу открывает готовый интерфейс для выполнения выбранной работы.

Внутри рабочего экрана не должно быть:

- кнопок `Открыть локации`, `Открыть приемку`, `Открыть склад`;
- повторного выбора того же сценария;
- дополнительной полосы этапов под заголовком;
- блока `Полное меню`;
- одинаковых KPI-карточек для всех сценариев;
- перехода в старый UI;
- информации, которая не влияет на текущее решение.

Мобильное меню не изменяется и не входит в этот план.

## 2. Новая навигационная модель

### 2.1 Верхний уровень

Верхняя навигация сохраняет раздел `Товары`.

Нажатие на `Товары` открывает desktop-мегаменю со сценариями.

### 2.2 Состав мегаменю

#### Работа сейчас

- `Очередь`

#### Подготовка

- `Локации`
- `Товарные шаблоны`
- `Заказы на партии`

#### Обработка партии

- `Приемка`
- `Фото`
- `Видео`
- `QR и паспорта`
- `На склад`

#### Результат

- `Склад`

### 2.3 Поведение пункта

Один клик по пункту:

1. выбирает сценарий;
2. закрывает мегаменю;
3. меняет URL;
4. сразу показывает рабочий интерфейс;
5. сохраняет сценарий в истории браузера.

Повторный клик и отдельный CTA не требуются.

### 2.4 Содержание пункта меню

Каждый пункт содержит только:

- название;
- одно короткое объяснение результата;
- иконку;
- счетчик, если он требует реакции.

Примеры полезных счетчиков:

- `Приемка — 3`;
- `Фото — 4 партии`;
- `Видео — 2 партии`;
- `На склад — 6 готовы`;
- `Очередь — 12 задач`.

Для `Локаций` и `Шаблонов` общее количество не показывается: оно не помогает выбрать следующее действие.

### 2.5 URL-модель

Рекомендуемые маршруты:

- `/admin/products/queue`
- `/admin/products/locations`
- `/admin/products/templates`
- `/admin/products/collection-orders`
- `/admin/products/acceptance`
- `/admin/products/photos`
- `/admin/products/videos`
- `/admin/products/identification`
- `/admin/products/stock-readiness`
- `/admin/products/warehouse`

Контекст выбранной сущности хранится в URL:

- `?batchId=...`
- `?itemId=...`
- `?locationId=...`
- `?productId=...`
- `?requestId=...`

Это позволяет открыть конкретную работу из очереди, истории или прямой ссылки.

## 3. Общий каркас рабочих интерфейсов

### 3.1 Заголовок

Рабочий экран содержит:

- название сценария;
- одну строку, объясняющую текущую задачу;
- основное бизнес-действие, если оно возможно.

Допустимые кнопки:

- `Создать локацию`;
- `Создать шаблон`;
- `Создать заказ`;
- `Принять партию`;
- `Сохранить фото`;
- `Запустить экспорт`;
- `Печать QR`;
- `Проверить и передать на склад`.

Недопустимые кнопки:

- `Открыть локации`;
- `Перейти в приемку`;
- `Открыть старый интерфейс`;
- `Подробнее`, если действие можно показать сразу.

### 3.2 Рабочая компоновка

Основной desktop-паттерн:

- слева список, очередь или структура;
- справа выбранная сущность и ее рабочие действия;
- при сложном редакторе рабочая область занимает всю ширину.

Выбор строки не переводит на отдельную страницу без необходимости. Детали открываются рядом или заменяют содержимое рабочей области.

### 3.3 Фильтры

Фильтры размещаются над рабочим списком и соответствуют только текущему сценарию.

Общие элементы:

- поиск;
- состояние;
- локация;
- товарный шаблон;
- период.

Неиспользуемые фильтры не показываются.

### 3.4 Состояния

Каждый сценарий должен иметь:

- загрузку;
- пустое состояние;
- ошибку загрузки;
- отсутствие результатов фильтра;
- несохраненные изменения;
- конфликт данных;
- успешное выполнение;
- отмененное действие.

Пустое состояние должно предлагать реальное следующее действие, а не переход в другой интерфейс.

### 3.5 Обратимые действия

После обратимого действия показывается сообщение с `Отменить`, если технически возможно.

Для опасных действий используется подтверждение:

- изменение серийного номера;
- изменение количества принятой партии;
- отмена приемки;
- отмена передачи на склад;
- списание группы Item.

Причина действия не обязательна.

### 3.6 История

История не занимает основную рабочую область.

Она открывается:

- в боковой панели выбранной сущности;
- через пункт `История изменений`;
- с фильтрацией по партии или Item.

## 4. Сценарий «Очередь»

### 4.1 Роль

Стартовый экран раздела `Товары`.

Он отвечает только на вопрос:

> Что администратор должен сделать следующим?

### 4.2 Структура

Одна рабочая очередь, разбитая на приоритетные группы:

1. ошибки проверки;
2. отсутствуют фото;
3. отсутствуют видео;
4. готовы к передаче на склад;
5. ожидают приемки.

Недавно завершенные партии в основную очередь не входят.

### 4.3 Строка партии

Показывается:

- шаблон;
- локация;
- номер партии;
- количество Item;
- фото `готово / всего`;
- видео `готово / всего`;
- состояние;
- одно следующее действие.

### 4.4 Действие

Кнопка строки сразу открывает требуемый интерфейс с выбранной партией:

- `Принять`;
- `Назначить фото`;
- `Подготовить видео`;
- `Исправить ошибки`;
- `Передать на склад`.

### 4.5 Что убрать

- общие складские показатели;
- стоимость партий;
- недавно завершенные партии;
- отдельные карточки с теми же счетчиками;
- несколько равнозначных действий в одной строке.

## 5. Сценарий «Локации»

### 5.1 Роль

Создание и поддержка точек происхождения товара.

### 5.2 Компоновка

Левая колонка:

- поиск;
- список локаций;
- состояние `активна / скрыта`;
- кнопка `Создать локацию`.

Правая область:

- форма выбранной локации;
- изображение;
- координаты;
- описание;
- переводы;
- настройки подписи на планете;
- связанные шаблоны и партии.

### 5.3 Создание

Нажатие `Создать локацию` очищает правую форму.

Поля:

- название;
- страна;
- широта;
- долгота;
- описание;
- изображение;
- переводы;
- параметры подписи.

### 5.4 Сохранение

Действия:

- `Сохранить`;
- `Скрыть`;
- `Восстановить`;
- `Отменить изменения`.

Сохранение не закрывает рабочую область и не возвращает пользователя в список.

### 5.5 Контекст связей

Связанные шаблоны и партии показываются компактным списком внизу формы.

Они нужны для оценки последствий изменения, а не как отдельный дашборд.

### 5.6 Что убрать

- дублирующую карточку локации над формой;
- отдельный переход в старый каталог;
- показатели количества паспортов или склада;
- повторный выбор `Локации` внутри экрана.

## 6. Сценарий «Товарные шаблоны»

### 6.1 Роль

Создание типа товара, по которому формируются заказы и партии.

### 6.2 Компоновка

Левая область:

- поиск;
- фильтр по локации, категории и публикации;
- плотный список шаблонов;
- кнопка `Создать шаблон`.

Правая область:

- редактор выбранного шаблона;
- live-preview клиентской карточки;
- связанные заказы, партии и складские Item.

### 6.3 Редактор

Группы полей:

#### Основное

- название;
- описание;
- описание места;
- категория;
- локация;
- цена.

#### Идентификация

- код страны;
- код локации;
- код товара;
- пример будущего серийного номера.

#### Публичный контент

- изображение;
- переводы;
- Wildberries;
- Ozon;
- публикация.

### 6.4 Действия

- `Сохранить`;
- `Опубликовать / Снять с публикации`;
- `Создать заказ на партию`;
- `Скрыть`;
- `Восстановить`.

`Создать заказ на партию` открывает сценарий заказов с уже выбранным шаблоном.

### 6.5 Что убрать

- партии и Item внутри раскрывающихся карточек шаблона;
- складские показатели в редакторе;
- дублирующую кнопку перехода в каталог;
- одинаковые сводные карточки над списком.

## 7. Сценарий «Заказы на партии»

### 7.1 Роль

Создание и контроль заданий на физическую партию.

### 7.2 Компоновка

Левая часть:

- список заказов;
- фильтры по состоянию и исполнителю;
- поиск по шаблону;
- кнопка `Создать заказ`.

Правая часть:

- форма заказа;
- состояние исполнения;
- связанная партия, если она создана;
- история действий.

### 7.3 Форма заказа

Поля:

- товарный шаблон;
- автоматически показанная локация;
- количество Item;
- исполнитель;
- заметка.

Исполнитель:

- общий пул;
- конкретный партнер;
- `Принять сразу`.

### 7.4 Автоприемка

При выборе `Принять сразу` в этой же форме появляются:

- GPS-широта;
- GPS-долгота;
- дата сбора;
- время сбора.

Основная кнопка меняется на:

`Создать и принять партию`.

### 7.5 Обычный заказ

Основная кнопка:

`Создать заказ`.

После создания экран остается на заказе и показывает его состояние.

### 7.6 Действия существующего заказа

- изменить количество до создания партии;
- изменить исполнителя;
- изменить заметку;
- отменить;
- восстановить;
- открыть созданную партию в релевантном сценарии.

### 7.7 Что убрать

- создание заказа из карточки шаблона как единственный путь;
- модальное окно без списка текущих заказов;
- показатели, не влияющие на выполнение заказа;
- переход через старую страницу товаров.

## 8. Сценарий «Приемка»

### 8.1 Роль

Зафиксировать физическое получение партии.

### 8.2 Компоновка

Левая колонка:

- только партии в пути;
- дата отправки;
- шаблон;
- локация;
- ожидаемое количество.

Правая рабочая область:

- данные партии;
- ожидаемое количество;
- поле фактического количества;
- предварительный состав Item;
- серийные номера;
- основное действие.

### 8.3 Приемка без расхождения

Администратор подтверждает количество и нажимает:

`Принять партию`.

### 8.4 Изменение количества

Если фактическое количество отличается:

1. интерфейс показывает разницу;
2. предупреждает об изменении состава Item;
3. показывает, какие Item будут добавлены или убраны;
4. требует подтверждение;
5. пересчитывает последовательность и серийные номера;
6. выполняет приемку.

### 8.5 После приемки

Вместо общей успешной страницы показываются следующие реальные действия:

- `Назначить фото`;
- `Подготовить видео`;
- `Печать QR`.

Каждая кнопка открывает соответствующий сценарий с этой партией.

### 8.6 Отмена приемки

Для принятой партии доступно вторичное действие:

`Отменить приемку`.

Перед подтверждением показываются последствия, но media и Item не удаляются.

### 8.7 Что убрать

- проверку каждого Item как принятого или отклоненного;
- несвязанные складские метрики;
- отдельную кнопку `Открыть приемку`;
- дублирование очереди над рабочей областью.

## 9. Сценарий «Фото»

### 9.1 Роль

Назначить одно фото каждому Item партии.

### 9.2 Вход

Если `batchId` не задан, показывается очередь партий без полного комплекта фото.

Строка очереди:

- шаблон;
- локация;
- Item `с фото / всего`;
- последнее изменение;
- действие `Начать`.

### 9.3 Рабочий режим партии

После выбора партии очередь заменяется полноценным Photo Tool внутри общего интерфейса:

- загрузка файлов;
- просмотр;
- сортировка;
- сопоставление с Item;
- прогресс покрытия;
- ошибки загрузки;
- сохранение.

Не должно быть дополнительного экрана с кнопкой запуска Photo Tool.

### 9.4 Постоянная информация

В закрепленной панели:

- партия;
- Item;
- назначено фото;
- осталось;
- несохраненные изменения.

### 9.5 Завершение

После сохранения:

- показывается результат;
- доступна отмена последнего назначения;
- предлагается `Перейти к видео` для той же партии;
- партия исчезает из очереди фото при полном покрытии.

### 9.6 Что убрать

- общий раздел `Медиа`;
- отдельную кнопку `Photo Tool`;
- карточки готовности, повторяющие сам редактор;
- переход через приемку.

## 10. Сценарий «Видео»

### 10.1 Роль

Создать одно финальное видео для каждого Item партии.

### 10.2 Вход

Если `batchId` не задан, показывается очередь партий без полного комплекта видео.

Строка очереди:

- шаблон;
- Item `с видео / всего`;
- наличие исходника;
- состояние последнего экспорта;
- действие `Начать`.

### 10.3 Рабочий режим партии

Video Tool открывается внутри сценария без промежуточного launcher-экрана.

Этапы самого инструмента допустимы, потому что они являются частью одной работы:

1. исходники;
2. редактор;
3. экспорт.

### 10.4 Постоянная информация

- выбранная партия;
- количество Item;
- число размеченных фрагментов;
- число готовых видео;
- ошибки рендера;
- ошибки загрузки.

### 10.5 Завершение

После успешного экспорта:

- партия исчезает из очереди видео;
- доступен просмотр результата по Item;
- предлагается `Проверить готовность к складу`.

### 10.6 Что убрать

- launcher со скачиванием как основной рабочий экран desktop-приложения;
- отдельную кнопку `Открыть Video Tool`;
- общую абстрактную карточку готовности media.

## 11. Сценарий «QR и паспорта»

### 11.1 Роль

Управление идентификацией Item после приемки партии.

### 11.2 Компоновка

Левая часть:

- выбор принятой партии;
- список Item;
- поиск по серийному номеру;
- выбор нескольких Item.

Центральная часть:

- preview этикетки;
- preview публичного паспорта выбранного Item.

Правая часть:

- настройки макета;
- состав полей;
- размеры;
- основное действие печати.

### 11.3 Действия Item

- открыть паспорт;
- скопировать ссылку;
- показать QR;
- изменить серийный номер;
- восстановить предыдущий серийный номер.

Изменение серийного номера выполняется только для одного Item и требует подтверждения.

### 11.4 Печать

Доступные действия:

- `Печатать выбранные`;
- `Печатать всю партию`;
- `Сохранить PDF`.

Печать не меняет состояние партии.

### 11.5 Что убрать

- отдельный переход из приемки в QR-сервис;
- выбор партии после того, как она уже передана через URL;
- показатели media, если они не влияют на печать;
- отдельную кнопку открытия паспорта вне списка Item.

## 12. Сценарий «На склад»

### 12.1 Роль

Вручную проверить готовность партии и завершить товарный процесс.

### 12.2 Компоновка

Левая колонка:

- партии с полным media;
- партии с неполным media;
- партии с ошибкой проверки.

Первыми показываются готовые к проверке.

Правая область:

- сводка выбранной партии;
- проверка каждого обязательного условия;
- список проблемных Item;
- основное действие.

### 12.3 Проверка

До запуска показывается:

- фото `готово / всего`;
- видео `готово / всего`;
- уникальные серийные номера;
- состояние партии.

Основная кнопка:

`Проверить и передать на склад`.

### 12.4 Успешный результат

В этой же области показывается:

- партия передана на склад;
- число добавленных Item;
- ссылка на отфильтрованный склад;
- действие `Отменить передачу`.

### 12.5 Ошибка

Общего сообщения недостаточно.

Показываются отдельные группы:

- Item без фото;
- Item без видео;
- дубли серийных номеров;
- недопустимое состояние партии.

Каждая строка ведет прямо в исправляющий сценарий с выбранным Item или партией.

### 12.6 Что убрать

- переход через приемку;
- ручное распределение после склада;
- общие KPI;
- кнопка `Открыть склад` как основной результат.

## 13. Сценарий «Склад»

### 13.1 Роль

Контроль Item, полностью завершивших товарный процесс.

### 13.2 Основной вид

Плотная таблица Item.

Колонки:

- фото;
- серийный номер;
- товарный шаблон;
- локация;
- партия;
- media;
- состояние;
- дата поступления;
- действия.

### 13.3 Фильтры

- поиск;
- локация;
- шаблон;
- партия;
- `на складе / списан`;
- наличие фото;
- наличие видео.

### 13.4 Карточка Item

Открывается в боковой панели:

- идентификация;
- фото;
- видео;
- паспорт;
- QR;
- исходная партия;
- складское состояние;
- история.

### 13.5 Действия

- списать;
- вернуть на склад;
- открыть паспорт;
- печатать QR;
- открыть партию;
- выбрать несколько Item для группового списания или возврата.

### 13.6 Списание

Списание:

- требует подтверждения;
- не требует причины;
- обратимо;
- сразу убирает Item из доступных к продаже;
- фиксируется в истории.

### 13.7 Что убрать

- отдельные уровни `локация → шаблон → партия → Item`, если они мешают поиску;
- распределение `STOCK_HQ → STOCK_ONLINE`;
- сводные карточки над таблицей;
- поля продаж и финансов в основном складском интерфейсе.

## 14. Взаимодействие между сценариями

Переход между сценариями допустим только как продолжение реальной работы.

Примеры:

- шаблон → создать заказ с выбранным шаблоном;
- очередь → открыть Photo Tool выбранной партии;
- приемка → назначить фото этой партии;
- фото → перейти к видео этой партии;
- видео → проверить готовность к складу;
- ошибка склада → открыть конкретный Item без media;
- склад → открыть паспорт конкретного Item.

При переходе контекст передается через URL. Пользователь не выбирает сущность повторно.

## 15. Визуальная иерархия

### 15.1 Общий стиль

Сохраняется существующая темная оболочка ZAGARAMI.

Для раздела `Товары` используется зеленый акцент только для:

- выбранного сценария;
- успешной проверки;
- подтвержденного завершения;
- основного действия.

### 15.2 Цвета состояний

- зеленый — готово или успешно;
- янтарный — требуется действие;
- красный — блокирующая ошибка;
- серый — неактивно или справочно;
- голубой — выполняющийся технический процесс.

### 15.3 Плотность

- таблицы и очереди плотные;
- формы разделены на смысловые группы;
- карточки используются только для самостоятельных объектов;
- обычные списки оформляются строками с разделителями;
- не более одного визуально доминирующего действия на экран.

## 16. Что должно исчезнуть из текущего прототипа

- `activeStage.to` как обязательная навигация в старый UI;
- глобальная кнопка `Открыть ...`;
- `StageRail` под заголовком;
- кнопка `Полное меню`;
- повторение пунктов мегаменю в рабочей области;
- универсальные `metrics`, `facts` и одинаковые preview-блоки;
- отдельный пункт `Распределение`;
- общий пункт `Медиа`;
- декоративные данные без действия;
- статические демонстрационные числа после подключения реальных API.

## 17. Компонентная модель

### 17.1 Общая оболочка

`ProductsWorkspaceShell` отвечает только за:

- desktop-мегаменю;
- текущий маршрут;
- заголовок рабочего сценария;
- общие уведомления;
- ACL;
- сохранение выбранного контекста в URL.

### 17.2 Самостоятельные сценарии

Каждый сценарий имеет собственный компонент:

- `ProductsQueueWorkspace`
- `LocationsWorkspace`
- `ProductTemplatesWorkspace`
- `CollectionOrdersWorkspace`
- `AcceptanceWorkspace`
- `PhotoWorkspace`
- `VideoWorkspace`
- `IdentificationWorkspace`
- `StockReadinessWorkspace`
- `WarehouseWorkspace`

Сценарии не строятся из одного универсального шаблона.

### 17.3 Допустимые общие компоненты

- строка поиска;
- панель фильтров;
- split-view;
- таблица;
- боковая панель сущности;
- подтверждение опасного действия;
- журнал изменений;
- состояния загрузки и ошибки.

Общим может быть UI-примитив, но не структура бизнес-сценария.

## 18. Порядок проектирования

Каждый сценарий проходит отдельно:

1. информационная архитектура;
2. wireframe desktop;
3. список состояний;
4. список действий;
5. проверка на дубли;
6. визуальный макет;
7. интерактивный прототип;
8. подключение реальных данных;
9. UX-проверка на реальной задаче.

Рекомендуемая очередь:

1. `Очередь`;
2. `Приемка`;
3. `Фото`;
4. `Видео`;
5. `На склад`;
6. `Склад`;
7. `Заказы на партии`;
8. `Товарные шаблоны`;
9. `Локации`;
10. `QR и паспорта`.

## 19. Критерии приемки UX

Сценарий считается спроектированным правильно, если:

- после одного клика в мегаменю видна рабочая задача;
- нет кнопки перехода в старый UI;
- пользователь не выбирает сценарий повторно;
- выбранная сущность не теряется между связанными сценариями;
- на экране одно основное действие;
- все данные помогают выполнить это действие;
- блокирующая ошибка показывает конкретные Item;
- опасное действие подтверждается;
- обратимое действие можно отменить;
- история доступна, но не мешает работе;
- URL восстанавливает тот же сценарий и выбранную сущность.

## 20. Граница текущего этапа

На этом этапе проектируется только desktop UX/UI раздела `Товары`.

Не входят:

- мобильное меню;
- разделы `Продажи`, `Планета`, `Система`;
- изменение бизнес-логики продаж;
- уведомления;
- новая визуальная система всего продукта.
